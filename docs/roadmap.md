# 路线图

现行规划，只写还没做或还没收口的事。已交付能力见 [CHANGELOG](../CHANGELOG.md) 与各现行文档，不在这里复述成「当前阶段」。

产品边界不变：自托管、每成员一台远程电脑、普通用户只描述目标。不回到本地 CLI、Coding Agent 或 Worker 进程内 cron。

## 现在（已具备）

- 工作台：对话、Skill、记忆、自动任务、文件与产物。
- 控制面：组织与角色、OIDC、平台模型、版本化 Skill、SSE / Worker 租约。
- 工作区：上传走对象存储再同步 `/work`；预览走同源跳转。
- 部署：单机 Compose；k3s + JuiceFS CSI；控制面可多副本（Helm 默认仍是 1）。
- 渠道：飞书私聊投递（有绑定才生效）。
- 知识库：可选 MCP 检索，不是默认必装。
- 自动任务 V1：一次性 / cron（最短 1 小时），Postgres `SKIP LOCKED` 认领，创建者身份投递。

上线前仍缺的是验收，不是功能清单：生产身份与 CSRF、对象存储、限流/配额、备份恢复、工作台到 Worker 的纵向验收。集群多副本与滚动发布也还没有当成已验收能力。

## 近期：把现有面做完整

优先收口已经露出的半截能力，而不是开新子系统。

1. **自动任务闭环**
   - 对话里用自然语言创建 / 改任务（Worker 写库或平台 Skill）。
   - 有飞书绑定则把每次结果推回私聊。
   - 审批挂起保持 `active`（V1 已如此），列表把「等待确认」说清楚。
2. **飞书与知识库的缺口**
   - 飞书：关键进度摘要（长任务不能只靠「完成后点开工作台」）。
   - 知识库：扫描件 OCR、外部 RAG provider 仍明确不做，除非有组织真在用知识库并卡住。
3. **生产门禁**
   - 限流与每组织配额（自动任务已经有条数上限，对话和上传还没有对等的成本闸）。
   - 备份 / 恢复演练写进发布检查，而不是只写在部署文档里。
   - 控制面多副本按真实负载验一轮 offer / SSE / 自动任务认领。

## 下一阶段：触发从「到点」扩展到「出事」

时间触发已经够用。下一档价值在事件，不在把 cron 缩到 5 分钟。

- **事件触发**：飞书关键词以外的 webhook / GitHub / 内部业务回调。调度器仍然只负责 when，what 继续走 `appendMessage`。
- **通知**：工作台未读 + 飞书；不做「有变化才通知」的静默监控，除非先有便宜的无 LLM 探测。
- **运行观测（管理端）**：按组织看成功率、耗时、排队、失败原因；默认不展示消息正文。这是排障和成本控制，不是普通用户功能。
- **可信任务**：组织管理员可把指定自动任务标为可跳过外部确认。默认策略不变。

## 更后面（建议，不是承诺）

按「远程电脑替人干活」取值，而不是按 Coding Agent 补功能。

| 方向 | 为什么值得 | 不要做成 |
|---|---|---|
| 团队只读共享自动任务 / 对话 | 早会简报、值班摘要需要别人看得见 | 团队服务账号代跑（配额和审计会糊） |
| 产物模板与导出 | 简报、纪要、表格是当前默认工作 | 通用 Office 在线编辑、公开分享链接 |
| 移动端只读 + 确认 | 审批和看结果常发生在手机上 | 再做一套完整工作台 |
| 无 LLM 的便宜探测 | 目录有无新文件、连接器有无新消息，再决定要不要叫模型 | 每 5 分钟跑一轮 Agent |
| 子任务与 Skill 市场治理 | 组织会堆积 Skill 版本 | 把 Worker Core 开放成插件 SDK |

## 明确不做

- 低于 1 小时的重复自动任务、Worker 内 cron、独立调度微服务。
- 默认工具加回 Shell / Git / Patch / 任意后台进程。
- 普通用户自配模型、MCP 命令或权限档位。
- 以仓库和 PR 为中心的产品形态。

需要新能力时，优先加窄的控制面接口、版本化 Skill 或受管外部工具，见 [扩展 Kross](extensions.md)。

工作连接器（GitLab、Notion、邮件及后续办公系统）的产品决定和厂商调研见 [工作连接器](work-connectors.md)。
